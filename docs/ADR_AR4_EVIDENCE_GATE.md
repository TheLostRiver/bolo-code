# ADR · AR4 四个候选的证据门控决策

| | |
|---|---|
| 编号 | AR4 |
| 日期 | 2026-07-27 |
| 相关 | [ROADMAP.md](./ROADMAP.md) §13.10.2 AR4 · 看板第 19 位 |

ROADMAP 对 AR4 的规则原文：**「每个候选独立形成 implement / defer / reject
决策，带证据、风险、回滚和重开条件」**，且**「缺少真实需求必须书面关闭，
而不是留永久待办」**。

本文逐条执行那条规则。**四个候选全部关闭**——不是因为它们没价值，
而是因为准入条件逐条核对后都不成立，其中一个的前提甚至根本不存在。

---

## 1. U5 · 真 Ink / IDE bridge

**决策：不实施（closed）**

**准入条件**：AR1 pager 的可复现能力缺口，或 IDE 跳转明显减少 diff 操作步骤。

**证据**：

- 终端侧已有可滚 diff 面板（`packages/cli/src/tui/diffPane.ts`）与审批面板，
  view-model 在 `packages/core/src/diffViewModel.ts`（446 行，有键位纯函数与整屏渲染）
- 本轮又给桌面端做了三栏外壳与内容卡片，diff 有独立的呈现路径
- **没有记录到任何「pager 做不到」的具体场景**。准入要的是「可复现的能力缺口」，
  而不是「换个技术栈可能更好」

**「IDE 跳转」那半条另有反证**：调研发现 Codex App 的「在编辑器打开文件」
**约 80% 失效**（见 [DESKTOP_DESIGN.md](./DESKTOP_DESIGN.md) §3）。
边界交接是公认难做稳的一类，在没有需求驱动时主动去碰它属于自找麻烦。

**重开条件**：出现具体的、可复现的 pager 能力缺口（写清楚是什么操作做不到），
或有人真实反馈 diff 浏览步骤过多。

## 2. Adaptive thinking（按情境自动调 effort）

**决策：不实施（closed）**

**准入条件**：固定语料显示静态 effort 有**稳定劣势**。

**证据**：

- effort 轨（E0–E9）已收口，是成熟的表驱动方言系统
  （`packages/providers/src/effortDialect.ts`：canonical 级别 + 每家 wire 映射）
- 用户可用 `/effort` 显式切换，`BOLO_EFFORT_LOOSE` 等开关齐备
- **没有做过对比基准，因此没有「稳定劣势」的证据**——而准入条件要的正是这个

**这不是可以靠推理补上的**：「自动调可能更好」是直觉，不是证据。
AR2B2 已经建了基准脚手架（`test-compact-benchmark.ts` 的做法可复用），
真要立项应先出对比数据。

**额外风险**：自动调 effort 会让**同一个 prompt 在不同时刻花不同的钱**，
而用户对成本的预期是稳定的。没有实测收益就引入这种不确定性，不划算。

**重开条件**：固定语料上跑出静态 effort 的稳定劣势（带数字）。

## 3. Hook trust UI

**决策：不实施（closed）**

**准入条件**：多 workspace 信任切换需求，且 CLI 文本无法安全表达。

**证据**：

- `packages/hooks/` 里**没有任何 trust 概念**（grep `trust` 零命中）——
  也就是说这不是「UI 缺失」，而是**整个信任模型都不存在**
- hooks 现由 `.bolo/hooks.json` 配置，与项目文件同权限边界：
  能改 hooks 的人本来就能改代码
- 未观察到多 workspace 之间需要区分信任的场景

**先做 UI 是顺序错的**：真要做，第一步是定义信任契约（谁信任什么、
边界在哪、失信时如何 fail-closed），那属于 packages 层的设计，不是一个面板。

**重开条件**：出现具体的多 workspace 信任场景，且能说清 `.bolo/hooks.json`
的现有权限边界为何不够。届时先立契约，再谈 UI。

## 4. 远程模型列表

**决策：不实施（closed）——准入前提本身不成立**

**准入条件**：**静态模型表**造成真实兼容故障，且 provider API 稳定。

**证据（这条最干脆）**：

**根本不存在静态模型表。** `model` 在配置里是**自由字符串**
（`packages/config/src/types.ts:24` `model?: string`），用户填什么就发什么，
Bolo 不维护任何白名单。所以「静态表造成兼容故障」这个前提无从谈起。

**本轮确实撞到过模型相关故障，但根因不是它**：中转返回
`HTTP 503` 却包着 `{"code":"model_not_found"}`。真正的问题是**错误解释按状态码
而非按 body 判断**，会告诉用户「这是上游问题，不是你的配置」，把人指向反方向。
已修（错误解释改为 body 优先于 status，见 [TOOLS.md](./TOOLS.md) §3.4）。

**这正是证据门控的价值**：如果不先找证据就实施，会做出一个远程模型列表，
而真实故障——错误信息把人指错方向——原封不动。

**另有红线约束**：远程列表意味着新增一个网络依赖与新的第三方接收方，
且在离线时必须有 fallback。为一个不存在的问题付这个代价不合理。

**重开条件**：出现**由模型名导致**的真实兼容故障，且已确认不是错误解释
或文档问题。

## 5. 前台命令自动后台化

**决策：不实施（closed）——但同一份证据指出了一个更小的真缺口，已修**

**准入条件**：前台超时造成的损失，大到值得引入一个模型没有要求的后台任务。

**证据（先量代价，而不是先设计方案）**：

读 `packages/tools/src/builtins.ts` 的超时分支发现，**部分输出本来就保留着**——
`err.stdout` / `err.stderr` 都进了 output。所以超时的真实损失不是「结果没了」，
而是**「跑到一半白跑，且模型不知道下一步」**：错误里只有 execFile 的 ETIMEDOUT，
没有任何一处提到 `run_in_background` 这条现成的路。

于是缺口比候选描述的小得多，也具体得多：**错误信息不可行动**。

**自动转后台的代价则是实打实的**：

- 凭空多出一个模型没要求的后台任务，以及一个它必须开始追踪的 shell id
- 「这一轮到底完了没有」变得含糊——而这正是 durable runtime 花了整条 DR 轨去消除的东西
- 命令有副作用时更糟：用户以为超时=停了，实际它还在跑

**已改的**：超时错误现在把出路写进去（重跑时用 `run_in_background`，或调高
`timeout`），并且**只在超时时写**——把「换后台跑」贴到一个语法错误上，
是在把模型往错误方向推。两个方向都有红灯验证（`test-bash-timeout-guidance.ts`）。

**重开条件**：出现具体案例，说明「模型看懂了出路仍然做不对」——也就是
可行动的错误信息**不足以**解决问题，而不是「自动化听起来更省事」。

## 6. LSP

**决策：暂缓（deferred）——不是关闭，附可判定的触发条件**

前五条都关掉了，这条**不关**。理由要说清楚，否则「暂缓」会变成
本文档开头批评的那种永久待办。

**证据（对它有利的一半）**：

符号级导航今天确实没有。`packages/tools/src/` 下是 Glob/Grep，
找一个类型定义要靠文本匹配——本轮为查 `McpServerConfig` 的字段就绕了几次。
这不是想象出来的缺口。

**证据（不足以立项的一半）**：

- 上述绕路都**成功了**，只是多花了几次工具调用。没有记录到任何一次
  「grep 找不到、于是做错了」——而准入要的是后者
- LSP 意味着**给每种语言起一个 language server 进程**，那是本仓明确不做的
  「代跑第三方进程」；要么退化成只支持 TypeScript，那又是另一回事了
- 体量上它不是一刀，是一条轨

**触发条件（任一成立即立项，先出契约再动手）**：

1. 记录到 **3 次以上**「文本搜索给出了错误答案并导致了错误改动」的具体案例
   （重命名撞同名符号、改错了重载、漏改一个实现）
2. 或出现一个**不需要额外进程**的方案（例如直接用仓库已有的 TypeScript
   编译器 API 做单语言符号索引）——那样代价面完全不同，得重新评

**为什么不现在就按 2 做**：TypeScript 是 devDependency，产物零运行时依赖是红线；
把编译器 API 拉进运行时要么破红线，要么做成可选能力——那是个需要先立契约的设计，
不是顺手一刀。

---

## 关于「关闭」的含义

四条都写了重开条件。**关闭不等于永远不做**，只等于「现在没有证据支持它，
所以不占用排期，也不留在待办里假装还活着」。

留一堆永久待办的代价是真实的：它们会让看板失去信号——
每一项都「还没做」，于是没有一项是紧迫的。
