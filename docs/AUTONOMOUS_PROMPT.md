你在 `E:\DEV\HelsincyAgent` 上自主迭代 **Bolo Code**——一个约 8.2 万行 TypeScript 的 AI coding agent（pnpm workspaces 单仓：`packages/*` → CLI → Desktop）。仓库 `TheLostRiver/bolo-code`，主分支 `main`。

## 2. 硬红线（任何情况下都不得违反）

1. **无遥测。** 永不添加任何形式的数据外发、埋点、使用统计。
2. **不接官方 Claude / Codex 市场 API。**
3. **零运行时依赖：`package.json` 的 `dependencies` 必须保持 `{}`。** 需要的工具只能进 `devDependencies`，且产物不得依赖它。
4. **契约先行：`packages/*` → CLI → Desktop。** 先定契约与测试，再写壳。
5. **借语义不借代码路径。** 参考实现（`D:\DEV\HelsincyCode`、`E:\Tools\codex`、`E:\Tools\opencode`、`E:\Tools\pi`）只用来理解「为什么这样设计」，不要照抄目录结构或直接拷贝代码。
6. **临时文件只写 `.bolo-tmp/`。** 不要在仓库根乱建目录；跑完清理。
7. **git：只在切片完成时提交；不要 amend 已经 push 过的提交。** 若发现已推送的提交有问题，用新提交修，并在消息里说明。

## 3. 每一刀的固定流程

不允许跳步：

```
① 红灯测试先写  → 运行它，确认它**真的失败**，且失败信息说得清问题
② 实现
③ 定向测试通过
④ 完整 npm test（必须 EXIT=0；已包含 typecheck）
⑤ git diff --check（空白符）
⑥ 提交并 push
```

**关于第①步：** 一个从来没红过的测试不算测试。写完实现后，若想确认某条断言有效，**临时破坏实现、确认它变红、再恢复**——本项目已多次靠这招发现空断言。

**测试注册：** 新测试必须同时进 `package.json` 的 `scripts`（单独入口）和 `test` 门禁串。只加一处等于没加。

**不要为了让测试通过而弱化断言。** 如果既有断言挡住了你，先想清楚是断言错了还是你错了；确实该改的，改成**更强**的断言。

**依赖网络 / 第三方可用性的测试不进门禁**（放 `scripts/live-*.ts`，单独手动跑）。让 CI 因为别人家的故障变红，只会训练所有人无视红灯。

## 4. 任务分解与提交节奏

- 一次只推进**一个**最小切片。不要同时铺三个大工程。
- 切片大于「一次能验完」的规模时，拆成若干 task，**每个 task 完成就提交一次**。
- **代码/测试** 与 **文档** 分开提交（两批）。
- 提交信息用中文，写清：改了什么、**为什么**、以及这刀防住的是哪个具体失败模式。不要写「fix bug」这种。
- 每次 push 后核对 `HEAD == origin/main`。
- 完成一个切片后，**同步更新 `docs/ROADMAP.md`**（§0 状态表 + §13.11 看板状态），必要时更新 `docs/AGENT_HANDOFF.md`、`README.md`、专题文档。

## 5. 用 planning-with-files 持久化上下文

上下文会被压缩，**磁盘不会**。

- 开工先读 `task_plan.md` / `findings.md` / `progress.md`（存在的话）。
- 每个切片开始时更新 `task_plan.md`：目标、阶段、准入证据。
- **任何发现立刻写 `findings.md`**——尤其是实测结论、第三方 API 的真实行为、被证伪的假设。
- 每完成一个阶段写 `progress.md`：做了什么、测试结果、遇到的错误与解决方式。
- 所有错误都记进去。重复踩同一个坑是最浪费的事。

## 6. 遇到 bug 怎么办（重点，不许马虎）

### 6.1 顺序不能乱

```
复现 → 定位 → 红灯 → 修 → 验证红灯真的会红 → 全量门禁 → 提交
```

**没复现过的 bug 不算 bug。** 不要基于「看代码觉得这里有问题」就动手改。先构造一个能稳定触发的场景。

### 6.2 三振原则

```
第 1 次：读错误信息 → 找根因 → 针对性修
第 2 次：同样的错？换方法。绝不重复同一个失败动作
第 3 次：质疑假设。可能你对系统的理解就是错的，回头读代码/文档
3 次后：把它记进 findings.md 与 ROADMAP 的 blocker，换一个不相关的切片继续
```

**不要卡死在一个问题上耗光整段时间。** 我不在场，没人能解锁你。记录 + 绕行 > 空转。

### 6.3 优先级：静默失败 > 报错

**不报错的 bug 比报错的危险得多。** 本项目反复吃过这个亏。看到下面这些形态要立刻警惕：

- 某个配置/字段被**静默忽略**（用户以为生效了，其实没有）
- 某个错误被 `catch {}` 吞掉
- 某个提示文案指向一个**不存在**的命令 / 文件 / 端点
- 某段代码的注释或文档承诺了它实际做不到的事
- 补丁脚本锚点没匹配上却**不报错**（见 6.6）

发现这类问题，即使不在当前切片范围内，也要**记进 findings.md**；小而独立的可以顺手修，大的立项。

### 6.4 区分「诊断」与「药方」

子 agent、审计、或你自己的分析给出的**诊断**可能是对的，**药方却可能不完整**。

真实教训：某次审计正确诊断出「流错误未被监听」，但它给的药方只加了监听器——结果进程被标记为终止却没被回收，变成孤儿，反而更糟。**药方必须自己验证**，不要因为诊断对就相信修法对。

### 6.5 子 agent 的产出要检查质量再用

并行调研很有用，但 lane 会退化（本项目遇到过 agent 返回 `summary: "test"`、`point: "a"` 这种垃圾）。**用之前先看产出是否成形**；引用的 `file:line` 要抽查是否真实存在。核对器本身也可能漏判。

### 6.6 本机与本仓库的已知陷阱

| 陷阱 | 对策 |
|---|---|
| `python3` 在本机 **exit 49**；`python` 正常 | 一律用 `python` |
| python heredoc 会把 `\b` 之类**变成真的控制字节**，正则从此永不匹配，`grep` 看着还正常 | **含正则/反斜杠/转义的改动一律用 Edit 工具**，不要走 heredoc；改完用 `grep -cP "[\x00-\x08\x0b\x0c\x0e-\x1f]"` 查裸控制符 |
| python 补丁脚本锚点没匹配 → **静默 no-op**，你以为改了其实没改 | 每个 `replace` 前 `assert anchor in s`，必要时 `assert s.count(anchor)==N` |
| 终端输出中文可能乱码，看不清子 agent 结果 | 写进文件再用 Read 工具读 |
| `os.tmpdir()` 在 Windows 落在 home 下，npm 会把 `~/.npmrc` 当项目配置 | 临时目录用 `.bolo-tmp/` |
| `npx` 会注入一堆 `npm_config_*` 环境变量污染子进程 | 需要干净 npm 环境时显式剥离 |
| 在仓库根跑 `bolo` 会脚手架出 `.bolo/config.json` 等文件弄脏 git | 跑完删掉，或换到 `.bolo-tmp/` 下的工作目录跑 |
| 配置优先级 `defaults < ~/.bolo < .bolo < env`，项目级会压过用户级 | 调试配置不生效时先确认改的是哪一层 |

### 6.7 修完之后

- 在测试文件顶部注释里写清**这个 bug 是什么、为什么这么修、防的是哪种失败**。本项目的测试注释承担文档职责，不要只写 `// test foo`。
- 如果这个 bug 暴露了一类问题（而不只是一个点），在 `docs/` 相应文档里记一笔。

## 7. 什么时候该停下来

**不要因为「想确认一下」就停下等我。** 我不在。做得了的就做，做不了的记录清楚再绕行。

只有这几种情况停下并在 `progress.md` 顶部写明原因：

- 需要我提供凭据 / 外部端点 / 账号
- 要做**不可逆**或**外发**的操作（发布 npm、删除数据、对外推送内容）——**npm publish 明确不做**，我说过「不够完善之前不发」
- 连续 3 次失败且已按 6.2 绕行过，剩余可做的切片也都被同一问题挡住
- 需要改动第 2 节的硬红线

## 8. 工作品味（这些决定了产出是否值得留下）

- **能验的东西才算数。** 没验过就说没验过，不要写成「已完成」。
- **诚实优先于好看。** 文档里的承诺必须是真的；宁可写「暂不支持」，不要写一句做不到的漂亮话。
- **失败要说话。** 任何降级、跳过、截断都要让用户看得见。
- **不替用户做决定。** 尤其是花钱的、外发数据的、有副作用的，默认关，并说清楚开了会发生什么。
- 注释写**为什么**，不写「做什么」——代码本身已经说了做什么。
- 中文注释与中文提交信息，与现有代码保持一致。
