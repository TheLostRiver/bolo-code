# ADR · Compaction 是否引入远端能力

| | |
|---|---|
| 编号 | AR2C |
| 状态 | **不实施（closed）**——不是挂起，不是待办 |
| 日期 | 2026-07-27 |
| 相关 | [ROADMAP.md](./ROADMAP.md) §13.10.2 · [COMPACTION.md](./COMPACTION.md) |

## 决定

**Compaction 保持 local-only。** 不引入远端压缩、不引入跨会话的 session-memory 服务。

按 ROADMAP §13.10.2 的原文要求，本项在无证据时**关闭而非永久挂起**——
所以本文是一个结论，不是一份待办。重开条件写在最后一节。

## 背景

AR2C 的准入条件是：**「A/B 已证明本地瓶颈且有真实跨会话需求」**。
AR2A、AR2B 均已收口，可以对照这两条逐一核对。

## 证据

### 一、本地不是瓶颈（实测）

`scripts/test-compact-benchmark.ts`（进门禁），本机实测：

```
turns= 20 msgs= 100 tok  11047→859 ×12.9  3ms  heap+0.1MB
turns= 80 msgs= 400 tok  44607→859 ×51.9  2ms  heap+0.1MB
scaling: 4× input → 1.2× time
```

- 压缩管道本身耗时 **个位数毫秒**，内存增长 **0.1MB**
- 4 倍输入只涨 1.2 倍时间，**没有二次行为**
- 真正的耗时在 summarizer 的那一次 API 调用上，而那与压缩在本地还是远端无关

**准入第一条不成立。** 本地压缩没有任何可测量的性能问题需要靠远端解决。

### 二、token 计数精度已由本地手段解决

引入远端的常见理由之一是「本地算不准 token」。这一条已被 AR2A0a 与 AR2B1 消掉：

- `hybridTokenCount` 在有 anchor 时用 **provider 返回的真实 input** 计锚定前缀，
  只估算其后的尾部——精度问题的作用面被结构性收窄
- AR2B1 用真实端点标定后修正了字符类别分类，最差低估从 **−53% 收到 −5.3%**
  （`scripts/test-token-estimate-accuracy.ts`）

### 三、没有真实的跨会话需求

未观察到需要跨会话共享压缩产物的场景。当前 resume 语义（从最后一个
`compact_boundary` 之后重建）在单机上已经完整工作。

**准入第二条不成立。**

## 考虑过的选项

| 选项 | 结论 |
|---|---|
| **local-only（选中）** | 无新增第三方接收方、离线可用、无新增失败模式 |
| 远端压缩服务 | ✗ 见下 |
| 跨会话 session-memory 服务 | ✗ 见下 |

## 为什么不做远端（逐条列出 ROADMAP 要求的四个面）

### 隐私

远端压缩意味着**把完整对话历史发给一个新的第三方接收方**。

这与项目第一条红线（**永不遥测**）在精神上直接冲突：遥测发的是元数据，
而压缩要发的是**正文全部内容**——比遥测严重得多。

同一判据在 web search 轨已经用过并写进 [TOOLS.md](./TOOLS.md) §3：
provider-hosted 搜索之所以可以默认开，正是因为「搜索由用户**本来就在对话的**
provider 执行，没有新增接收方」。远端压缩不满足这个条件——它会把历史发给
一个用户并未选择与之对话的服务。

### 离线

本地压缩在断网时仍可工作（summarizer 那一步失败会**完整回退**，见
COMPACTION.md §2.6b）。远端压缩把一条本可离线完成的路径变成必须联网，
换来的收益按上文是零。

### 兼容

远端方案会引入服务端版本与本地 transcript 格式的双向兼容问题：
旧客户端读新格式、新服务端处理旧会话、服务不可用时的降级路径——
三条都要额外维护，而当前 transcript 是纯本地文件，格式演进只需管一端。

### 失败回退

新增远端调用即新增一整类失败模式（超时、鉴权、限流、服务下线、
返回被截断的摘要）。当前 compact 的失败面已经收敛为两类且都有完整回退
（摘要失败 / 写盘失败，见 COMPACTION.md §2.6b）。远端会把这个面重新打开，
且其中「服务永久下线」一类**没有本地回退可言**。

## 附带结论：不引入真 tokenizer

同属 AR2B1 的决定，一并记录：真 tokenizer 要么联网取分词、要么引入
不可审计的 native 依赖或大体积 BPE 表——**两条都撞零运行时依赖红线**
（`dependencies` 必须保持 `{}`）。

已改为用真实端点标定 + 修正字符类别分类，精度已达可用（见上文证据二）。
`scripts/live-token-calibration.ts` 保留下来供随时复测，但它是**开发期工具**，
不进门禁、不进产物。

## 重开条件

出现下列**任一**情况时重新评估，并在本文追加修订而非另起：

1. 基准显示压缩管道耗时或内存进入**秒级 / 百 MB 级**（当前是毫秒 / 0.1MB）
2. 出现真实的跨设备或跨会话共享需求，且本地文件同步无法满足
3. 本地 token 估算在某个常用 provider 上重新出现 **>15% 的低估**，
   且无法用字符类别分类修正

前两条都不成立时，**不要**因为「参考实现有」而重开——
调研已确认参考实现的远端压缩同样是可选路径，且 Bolo 的红线更严。
